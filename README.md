# День 21. Индексация документов — Doc Index Lab

Локальный индекс документов с эмбеддингами, метаданными и сравнением двух стратегий нарезки (chunking).
Документ — «Моби Дик» Германа Мелвилла (Project Gutenberg #2701), главы 1–40: 362 тыс. символов, около 145 страниц.

## День 29. Оптимизация локальной LLM под задачу

Вкладка **«11 Оптимизация»** ([`app/optimize.py`](app/optimize.py)). Задача — ответы с цитатами по «Моби Дику»
(конвейер Дней 24 и 28) на `qwen2.5:3b` и GTX 1050 Ti с 4 ГБ видеопамяти. Поиск во всех профилях одинаковый, меняется только генерация:

| профиль | что изменено |
|---|---|
| `base` | как в Дне 28: Q4_K_M, промпт v1, temperature 0.1, max 700 токенов, окно 4096 |
| `params` | temperature 0, max 400 токенов (ответу хватает ~150–330), окно 3072 (промпт ~1000–2100 токенов) |
| `prompt` | + шаблон v2: сначала дословные цитаты, потом ответ (порядок полей JSON-схемы задаёт порядок генерации), 3 лучших отрывка, вопрос до и после отрывков, правила перевода, пример |
| `q3` / `q5` / `q8` | лучший профиль (`params`) на квантованиях Q3_K_M / Q5_K_M / Q8_0 |
| `…-fa` | после включения в Ollama `OLLAMA_FLASH_ATTENTION=1` и `OLLAMA_KV_CACHE_TYPE=q8_0` |

Качество по эталону оценивает `gpt-4.1` (как в Дне 28), «не знаю» — код; 10 вопросов × 3 прогона.
Скорость и ресурсы (ГБ = 1024 МиБ) считаются по данным Ollama (загрузка модели, чтение промпта, выдача токенов) и по `/api/ps` с `nvidia-smi`.
Также в профиле: окно контекста передаётся в `llm.chat(num_ctx=…)`; проверка смысла идёт сразу после генерации,
а реранкер — после неё, поэтому на одну перезагрузку модели в видеопамяти меньше.

  - Значит, для роста качества нужна модель крупнее или облачный судья смысла, а не настройки 3B.
- **Поиск.** На 4 из 9 вопросов нужного отрывка нет в контексте даже у gpt-4.1: это потолок поиска, а не генерации.

Вкладка **«10 Локально vs облако»** ([`app/local_vs_cloud.py`](app/local_vs_cloud.py)). RAG-конвейер Дней 21–24
целиком работает на этом компьютере:

| Этап | Где выполняется |
|---|---|
| индекс Недели 6 (главы 1–40 «Моби Дика», стратегия structure) | SQLite `data/index.db` |
| эмбеддинг вопроса | `bge-m3` в Ollama, GPU |

`gpt-4.1`** (инструмент измерения, не часть системы; «не знаю» оценивает код). 10 контрольных вопросов Дня 22 ×

- **Полностью локальная система работает и безопасна, но отвечает по существу редко.** Поиск находит нужные отрывки
  одинаково для всех (он общий), а слабое звено — маленькая модель: она плохо пересказывает английский текст по-русски
  («кость **жирафа**» вместо sperm whale, хозяин гостиницы «Хоса Гусси»), и защита Дня 24 такие пересказы не выдаёт —
  отсюда 63–70% ответов «не знаю» или «ответ цитатами». Выдуманных ответов при этом нет: источники и подтверждённые

- **Облачная `gpt-4.1` на том же локальном поиске — в 2,6 раза точнее** (60% против 20–23% верных) и **в 6–7 раз

  вопрос про бритьё: нужного отрывка нет среди 5 найденных, и она честно отвечает «не знаю».

  (то ответ, то «не знаю»), `llama3.2:3b` предсказуемее по времени.
- **Компромисс**: локально — приватность (книга и вопросы не покидают компьютер), работа без интернета и без оплаты,
  но ~25 с на ответ и 20–23% точности; облако — качество и скорость ценой отправки вопроса и отрывков наружу.
  Поиск, цитаты и «не знаю» стоит держать локально в любом случае: они дешёвые (0,02 с) и защищают от галлюцинаций.

Похожесть ответов между прогонами (0,98 у `qwen2.5:3b`) выше, чем у `gpt-4.1` (0,81), потому что у локальной модели
большая часть ответов — одинаковое «Не знаю…», а не потому что её ответы стабильнее по содержанию.

## День 25. Мини-чат с RAG и памятью задачи

Вкладка **«09 Чат»** ([`app/chat.py`](app/chat.py)): чаты с историей в SQLite (`data/chat.db`), на каждый вопрос — поиск
по книге и ответ по конвейеру Дня 24 (порог «не знаю» → JSON-ответ → проверка цитат → проверка смысла), и **всегда блок
источников**: подтверждённые источники, либо явное «источников не найдено» со списком проверенных отрывков, либо пометка
«служебная реплика — поиск не нужен».

```
сообщение ─► ПАМЯТЬ ЗАДАЧИ: LLM извлекает изменения (JSON-схема), код решает, что принять
          │    цель ─ ставится один раз, меняется только по явной просьбе
          │    уточнения, ограничения, термины ─ накапливаются без дублей (из обычных вопросов не пополняются)
          │    «только главы 1–20» ─ распознаёт код → фильтр поиска
          ├─ служебная реплика (цель / ограничение / термин) ─► «Записал в память задачи: …»
          ├─ «подведи итог» ─► сводка по цели только из подтверждённых ответов + объединённые источники
          └─ вопрос ─► самостоятельный поисковый запрос: термины → значения («гарпунщик» → «Квикег»),
                       «А Стабб?» → «Кто такой Стабб?», «Какому идолу он…» → «Какому идолу Квикег…»
                     ─► RAG (воронка в пределах глав) + память задачи и 3 последних обмена репликами в промпте
```

**Панель «Память задачи»** справа показывает вживую: цель (с какого хода), диапазон глав, что пользователь уточнил,
ограничения, термины — с номером хода; то, что изменилось на последнем ходе, подсвечено. Память можно сбросить.

**Что пришлось решать кодом, а не моделью** (`qwen2.5:3b`):
- Тип реплики: модель считала «Отвечай кратко…» вопросом и запускала поиск → правила: «?» или вопросительное слово — вопрос;
  иначе служебная реплика.
- Переписывание уточняющих вопросов: модель подменяла вопрос («А Стабб?» → «Кто такой Старбек?», «Из чего нога капитана?» →
  «Кто из гарпунщиков приписан к капитану?»), склеивала с прошлым вопросом и выдумывала имена («капитан Марли»). Теперь
  сначала детерминированные правила (имя из недавних вопросов вместо местоимения, подстановка в эллипсис), модель — только
  если имени нет, и её вариант принимается, только если в нём остались все слова вопроса, нет новых имён и это один вопрос.
- Термины и диапазон глав из явных формулировок распознаются шаблонами; модель «находила» термины в обычных вопросах
  («Старбек — офицер») — из вопросов память больше не пополняется.
- Ответ на китайском (`qwen` иногда переключает язык): повтор с требованием русского, а если не помогло — пересказ не выдаётся.

## День 24. Цитаты, источники и анти-галлюцинации

Вкладка **«08 Цитаты»** ([`app/grounded.py`](app/grounded.py)). Ответ на вопрос — только с источниками и дословными цитатами,
а всё, что можно проверить кодом, проверяет код, а не модель:

```
вопрос ─► воронка Дня 23 (top-20 → косинус ≥ 0,45 → реранкер ≥ 0,65 → top-5)
      ─► ПОРОГ УВЕРЕННОСТИ: лучшая оценка реранкера < 0,80 или отрывков нет ─► «Не знаю» + просьба уточнить (без LLM)
      ─► LLM отвечает JSON по схеме {status, answer со ссылками [n], quotes [{source, quote}], clarify}
      ─► цитаты ищутся в тексте отрывков: дословно → почти дословно (≥80% слов, заменяется настоящим текстом)
         → в другом отрывке (источник исправляется) → иначе отклоняется
      ─► источники (source + section + chunk_id) собирает код по подтверждённым цитатам и ссылкам [n]
      ─► нет ни одной подтверждённой цитаты ─► «не знаю»
      ─► смысл ответа ↔ цитаты: судья (да / частично / нет) + кросс-энкодер «цитаты по теме»
           «нет» и цитаты сами отвечают на вопрос (реранкер ≥ 0,80) ─► ОТВЕТ ЦИТАТАМИ, пересказ не выдаётся
           «нет» и цитаты не по вопросу ─► «не знаю»
```

- **JSON по схеме**: для Ollama — structured outputs (`format` = JSON Schema), у ai-public/NVIDIA — `response_format: json_object`
  (если провайдер его не знает — запрос повторяется без него).
- **«Не знаю»** всегда с причиной и просьбой уточнить: «назовите персонажа, место или событие точнее» + подсказки — главы,
  к которым ближе всего вопрос. Порог уверенности меняется на странице.
- **Защита от инструкций в тексте**: отрывки передаются в `<source id=… chapter=…>`, закрывающие теги внутри текста экранируются,
  а модели сказано, что это цитаты, а не указания.
- **Почему смысл проверяет судья, а не реранкер.** Реранкер оценивает «про это ли текст», а не «следует ли утверждение из текста»:
  на цитату «fashioned from the polished bone of the sperm whale’s jaw» утверждения «нога из кости кашалота» и «нога из кости
  жирафа» получили 0,99 и 0,99, «из дерева» — 0,94. Судья (даже 3B) ловит такие подмены, поэтому он главный сигнал, а реранкер —
  вспомогательный «цитаты по теме ответа».

### Проверка на 10 контрольных вопросах (`qwen2.5:3b` отвечает и судит)

| Проверка | Результат |
|---|---|
| ответов по существу | 4 из 10: 3 пересказом, 1 цитатами |
| **источники в каждом ответе** | **4 из 4** |
| **цитаты в каждом ответе** | **4 из 4**; подтверждено текстом 13 из 13 цитат, дословно 11 |
| **смысл ответа ↔ цитаты** | выданные ответы: «частично» 3, «нет» 0; **3 пересказа не выданы** — противоречили своим цитатам |
| «не знаю» на вопросе-ловушке | 1 из 1 (на пороге уверенности, до вызова LLM) |
| лишние «не знаю» на вопросах с ответом | 5 из 9 |
| верно по эталону (судья 3B) | 1 верно, 2 частично |

**Что видно:**
- **Цитаты маленькая модель копирует хорошо** (13 из 13 нашлись в тексте), а **пересказывает плохо**: «sperm whale» у `qwen2.5:3b`
  стабильно превращается в «жирафа», доля добычи — в «место в Библии», погибшие китобои — в экипаж, «затянутый в лёд».
  Раньше (День 22–23) такие ответы уходили пользователю; теперь проверка смысла их отсекает: вместо выдумки — ответ цитатой
  из книги или честное «не знаю».
- **Цена — осторожность**: 5 вопросов с ответом получили «не знаю» (модель сама сочла, что ответа нет, или не дала цитат,
  или пересказ не прошёл проверку). Это лучше галлюцинаций, но с сильной моделью (ai-public/NVIDIA, выбирается в шапке)
  таких отказов должно быть меньше — проверка запускается кнопкой на вкладке.
- **Судья 3B ненадёжен как оценщик верности**: ответ цитатой про «sperm whale’s jaw» на вопрос о ноге Ахава он счёл неверным.
  Поэтому «не знаю» оценивает код (на ловушке — верно, на вопросе с ответом — промах), а для честных цифр нужен сильный судья.

## День 23. Реранкинг, фильтрация и query rewrite

После векторного поиска добавлен второй этап — воронка ([`app/rerank.py`](app/rerank.py)):

```
вопрос ─► rewrite: raw | en (перевод) | hyde (гипотетический отрывок) ─► bge-m3: top-K до (20)
      ─► фильтр 1: косинус ≥ sim_min
      ─► реранкер Qwen3-Reranker-0.6B (кросс-энкодер в Ollama): P(yes) «отрывок отвечает на вопрос»
      ─► фильтр 2: оценка ≥ rel_min ─► сортировка по оценке ─► top-K после (5) ─► LLM
```

- **Реранкер** — `B-A-M-N/qwen3-reranker-0.6b-fp16` в Ollama (1,5 ГБ, ~0,3 с на кандидата на GTX 1050 Ti). Он читает вопрос
  и отрывок вместе и отвечает yes/no; оценка = P(yes) / (P(yes) + P(no)) по `logprobs` первого токена (`/api/generate`, `raw`).
  Сборка `dengcao/Qwen3-Reranker-0.6B:Q8_0` не годится: у неё равномерные logprobs (≈ −11,9 у всех токенов).
- **Query rewrite** — LLM переводит вопрос на английский (`en`) или пишет короткий «отрывок в духе книги» (`hyde`); переписывания
  и оценки реранкера кэшируются в `data/rerank-cache.json`.
- **Пустой контекст** — если фильтры отсекли всё, модель получает «подходящих отрывков нет» и должна честно отказаться.
- **Вкладка «05 Вопрос · RAG»** — теперь три ответа рядом: без RAG / базовый RAG / RAG + rerank; под ними блок «Как искал
  улучшенный RAG»: переписанный запрос, воронка (20 → прошли косинус → прошли реранкер → в модель) и путь каждого кандидата
  с причиной отсева. Все параметры воронки настраиваются на странице.
- **Вкладка «07 Реранкинг»** — эксперимент подбора порогов, таблица режимов, живая настройка (метрики пересчитываются в браузере
  при движении ползунков), кривая «порог реранкера → качество» и разбор вопросов без ответа.

### Подбор порогов (эксперимент)

34 вопроса: 29 с известной главой (20 из Дня 21 + 9 из Дня 22) и 5 без ответа в индексе ([`eval/noanswer.json`](eval/noanswer.json):
собака Ахава и 4 вопроса о событиях после главы 40). Для каждого вопроса и режима запроса — top-20 кандидатов, реранкер оценивает
каждого один раз (≈10 минут), дальше метрики любых порогов считаются без обращения к моделям:
**hit@1** — первый отрывок контекста из нужной главы; **hit@K** — нужная глава есть в контексте; **точность** — доля отрывков
контекста из нужной главы; **пусто (без ответа)** — доля вопросов без ответа, где фильтр отсёк всё, то есть честный отказ.

| Режим | hit@1 | hit@K | точность | отрывков | пусто (без ответа) | отрывков (без ответа) |
|---|---:|---:|---:|---:|---:|---:|
| Базовый (День 22): вопрос как есть, top-5 | 86% | 97% | 62% | 5,0 | 0% | 5,0 |
| только порог косинуса ≥ 0,45 | 86% | 97% | 68% | 4,2 | 40% | 2,0 |
| только реранкер ≥ 0,65 | 90% | **100%** | 74% | 4,4 | 60% | 0,8 |
| **косинус ≥ 0,45 + реранкер ≥ 0,65** (выбрано) | **90%** | 97% | **79%** | 3,4 | **100%** | **0,0** |
| rewrite en (перевод), top-5 | 79% | 93% | 57% | 5,0 | 0% | 5,0 |
| rewrite HyDE, top-5 | 62% | 90% | 50% | 5,0 | 0% | 5,0 |
| перевод + фильтр + реранкер | 79% | 93% | 70% | 3,8 | 60% | 1,2 |
| HyDE + фильтр + реранкер | 76% | 93% | 69% | 3,6 | 40% | 1,0 |

Выбор — сетка по режиму запроса, порогу косинуса (0,30–0,50) и порогу реранкера (0–0,95): максимум hit@1 + hit@K + точность +
½·честные отказы при условии, что hit@K хуже лучшего не больше чем на один вопрос и ни один вопрос с ответом не остаётся без контекста.
Итог: **вопрос как есть, top-20 → косинус ≥ 0,45 → реранкер ≥ 0,65 → top-5**.

**Что видно:**
- **Реранкер — главный вклад.** Он поднимает нужный отрывок на первое место (hit@1 86 → 90%) и выкидывает «соседей по смыслу»:
  точность контекста 62 → 74%. Отсекает и мусор на вопросах без ответа: 5 → 0,8 отрывка.
- **Порог косинуса сам по себе слабый** — у bge-m3 косинусы лежат в узкой полосе 0,4–0,6: при 0,45 немного помогает, при 0,5 уже
  режет нужное (hit@K 97 → 72%). Но вместе с реранкером он убирает последние «пограничные» отрывки: на всех 5 вопросах без ответа
  контекст пустой, и модель честно отказывается. Цена — один вопрос из 29 (hit@K 100 → 97%).
- **Query rewrite с маленькой моделью вредит.** `qwen2.5:3b` переводит «Измаил» как «Izmael», склеивает слова через «+»,
  в HyDE выдумывает сцены — поиск по такому запросу хуже, чем по исходному вопросу: многоязычная bge-m3 и так понимает русский
  (hit@1 86% → 79% у перевода, 62% у HyDE). Rewrite реализован и включается на странице; с сильной моделью из ai-public/NVIDIA
  эксперимент можно повторить (кнопка на вкладке «Реранкинг» использует модель из шапки).
- Пороги подобраны на тех же вопросах, на которых измерены, — на новых вопросах цифры будут чуть хуже.

### Ответы: базовый RAG против RAG + rerank (10 контрольных вопросов, `qwen2.5:3b`)

| | без RAG | RAG | RAG + rerank |
|---|---:|---:|---:|
| верно (судья 3B) | 1 | 1 | 2 |
| верно / частично (ручная сверка) | 0 / 0 | 2 / 3 | 1 / 5 |
| нужная глава в отрывках | — | 8 из 9 | 8 из 9 |
| промпт на вопросе без ответа | — | 1722 ток. | 248 ток. (отрывков 0) |

С 3B-моделью разница в ответах в пределах шума: и с хорошим контекстом она пересказывает английский текст с искажениями
(«кость суперменшона» вместо sperm whale). Улучшение видно на поиске и на отказах: меньше мусора в контексте, честный
отказ вместо выдумки, короче промпт. Фильтр может и навредить: на вопросе про хозяина гостиницы он отсёк отрывок из главы 2,
где было имя «Peter Coffin», и модель ответила «в отрывках ответа нет».

## День 22. Первый RAG-запрос

Агент отвечает на вопрос о книге в двух режимах сразу:

```
 вопрос ─────────────────────────────────────────────► LLM ──► ответ без RAG (по памяти)
    │
    └─► bge-m3 ─► top-5 чанков (стратегия structure) ─► вопрос + отрывки [1]…[5] ─► LLM ──► ответ с RAG и ссылками [n]
```

- **Поиск** — индекс Дня 21, стратегия `structure` (лучшая по итогам сравнения), top-k = 5 (можно 3 или 8).
- **Промпт с RAG** — отрывки пронумерованы и подписаны главой; модель обязана отвечать только по ним,
  ставить ссылки `[n]` и честно говорить «В найденных отрывках ответа нет», если ответа там нет.
- **LLM выбирается в шапке**: локальные модели Ollama (`ollama:qwen2.5:3b`) или модели ai-public / NVIDIA
  (ключи из `~/.secrets/…`, как в агенте Дня 6; в браузер не уходят). Для Ollama используется нативный `/api/chat`
  с окном `num_ctx = 4096`: через OpenAI-совместимый `/v1` Ollama молча обрезает длинный промпт с отрывками.

### Вкладки

- **05 Вопрос · RAG** — два ответа рядом. Ссылки `[n]` в ответе с RAG кликабельны и подсвечивают отрывок; под ответами —
  отрывки, которые получила модель (глава, сходство, «в нарезке →»). Для контрольного вопроса показаны ожидание,
  источник и попала ли нужная глава в отрывки.
- **06 Качество** — прогон 10 контрольных вопросов: ответ без RAG, ответ с RAG и оценка **судьи** (отдельно выбираемая
  модель) — «верно / частично / неверно» по эталону. Код отдельно проверяет, попала ли нужная глава в отрывки.
  Результаты каждой модели сохраняются в `data/rag-eval/<модель>.json`, прогоны разных моделей можно сравнить.

## Как это работает (индексация, День 21)

```
 Gutenberg (зеркало, один раз) ─► data/sources/pg2701.txt
   ─► очистка: шапка, лицензия, оглавление ─► главы 1–40 ─► абзацы
   ─► нарезка ─┬─ fixed ──────┐
               └─ structure ──┴─► bge-m3 (Ollama, GPU) ─► L2-норма ─► SQLite data/index.db

 браузер ── вопрос ──► сервер ── вектор вопроса ──► Ollama
                         └─ скалярное произведение со всеми чанками ─► top-k по каждой стратегии
```

## Две стратегии нарезки

| Стратегия | Как режет | Что знает о тексте |
|---|---|---|
| **fixed** — фиксированный размер | окно 400 токенов, перекрытие 60, граница сдвигается к пробелу | ничего: может начаться посреди предложения и захватить две главы |
| **structure** — по структуре | главы не пересекает; набирает целые абзацы до 400 токенов (минимум 150); длинный абзац — по предложениям, сверхдлинное предложение — по словам; перекрытие ≈60 токенов с начала предложения | главы, абзацы, предложения |

**Текст для эмбеддинга.** У structure перед чанком стоит «Moby-Dick — Chapter N. Title»: стратегия знает главу.
У fixed — только название книги: глав она не знает.

**Токены.** Токенизатор модели скрыт в Ollama, но Ollama сообщает число токенов во входе (`prompt_eval_count`).
Перед первой индексацией 20 образцов по 1500 символов отправляются в модель по одному; по ответам считается,
сколько символов приходится на токен (для этого текста ≈3,75). По этому коэффициенту режутся чанки.

## Метаданные чанка

| Поле | Пример |
|---|---|
| `chunk_id` | `structure-moby-0012` — стратегия, книга, номер |
| `source` | `gutenberg:2701` |
| `title`, `author` | `Moby-Dick; or, The Whale`, `Herman Melville` |
| `section` | `Chapter 2. The Carpet-Bag`; если чанк захватил две главы — `Chapter 1. Loomings → Chapter 2. The Carpet-Bag` |
| `chapters` | номера всех захваченных глав |
| `start`, `body_start`, `end` | позиции в очищенном тексте; `[start, body_start)` — перекрытие с предыдущим чанком |
| `tokens`, `overlap_tokens`, `chars` | размер |
| `starts_mid_sentence`, `ends_mid_sentence` | начинается / обрывается посреди предложения |
| `vector` | эмбеддинг, 1024 × float32, длина 1 (BLOB в SQLite) |

Векторы нормализованы (L2), поэтому косинусное сходство — это скалярное произведение. В интерфейсе
сходство показано в диапазоне 0–1 как (1 + cos) / 2.

## Интерфейс (вкладки)

- **01 Индекс** — конвейер индексации, документ, модель и видеопамять, кнопки «Построить индекс» / «Построить заново»,
  журнал этапов вживую с прогрессом, карточки стратегий (чанки, токены, размерность, время, отпечаток) и пример
  одного чанка со всеми метаданными и началом вектора.
- **02 Нарезка** — глава книги в двух колонках: как её разрезала каждая стратегия. Чанки подсвечены поочерёдно,
  перекрытие заштриховано, ✂ — разрез посреди предложения. Клик по чанку — метаданные и вектор.
- **03 Сравнение** — вывод, таблица метрик с победителем по каждой строке, гистограммы размеров чанков,
  hit@k / MRR и таблица контрольных вопросов: на каком месте нашлась нужная глава.
- **04 Поиск** — вопрос по-русски или по-английски, результаты в двух колонках (по стратегии), сходство, глава,
  отметки «захватывает 2 главы» / «обрыв посреди предложения», переход «показать в нарезке».
  Для вопроса из примеров правильная глава известна: карточки из неё отмечены ✔.

## Сравнение стратегий

Результаты на главах 1–40 (`bge-m3`, GTX 1050 Ti):

| Метрика | fixed | structure |
|---|---:|---:|
| чанков | 286 | 339 |
| медиана / σ размера, токенов | 399 / 16 | 356 / 64 |
| мин – макс, токенов | 122 – 400 | 119 – 481 |
| в диапазоне 150–450 | 99,7% | 98,2% |
| перекрытие (доля повторно проиндексированных токенов) | 15,2% | 17,2% |
| обрываются посреди предложения | **96,2%** | **0,9%** |
| начинаются посреди предложения | 94,4% | 11,2% |
| захватывают две главы | **15,0%** | **0%** |
| время индексации | 76 с | 79 с |
| hit@1 / hit@3 / hit@5 | 80% / 90% / 95% | **95% / 100% / 100%** |
| MRR@10 | 0,871 | **0,967** |
| hit@1, вопросы по-русски / по-английски | 79% / 83% | 93% / 100% |

**Выводы.**
- **fixed** даёт идеально ровные чанки (σ = 16 токенов), но почти каждый обрывается посреди предложения,
  а каждый седьмой склеивает конец одной главы с началом другой. Такой чанк «размазан» по двум сценам,
  и его вектор хуже совпадает с вопросом про одну из них: на вопросах про Илию (гл. 19) и Старбека (гл. 26)
  нужная глава у fixed только на 4-м и 6-м месте.
- **structure** чуть неравномернее по размеру, зато чанки — законченные куски текста одной главы, а в текст
  для эмбеддинга попадает название главы. Это даёт +15 п.п. hit@1 и MRR 0,97 против 0,87.
- Цена structure — на 18% больше чанков и чуть больше перекрытие: время индексации почти то же (79 с против 76 с).
- Многоязычная `bge-m3` уверенно находит места в английском тексте по русским вопросам (hit@1 93% у structure).

Контрольные вопросы — [`eval/questions.json`](eval/questions.json): 20 вопросов (13 по-русски, 7 по-английски)
с ожидаемой главой и словами-доказательствами. Если слов нет в указанной главе, вопрос помечается
«не подтверждён текстом» и в метрики не идёт. Место засчитывается, если чанк захватывает нужную главу.

## Запуск

1. Установите [Ollama](https://ollama.com) и скачайте модель (около 1,2 ГБ):
   ```bash
   ollama pull bge-m3
   ```
2. Запустите сервер:
   ```bash
   run.bat
   ```
3. Откройте <http://127.0.0.1:5210> → «Построить индекс». Книга скачается сама.
   На GTX 1050 Ti (4 ГБ) индексация занимает около 2,5 минуты (≈1,6 тыс. токенов/с, модель целиком в видеопамяти).

Индексация из терминала: `python app/indexer.py` (`--rebuild` — с нуля).

**Повторный запуск** сверяет отпечаток варианта: sha256 текста, параметры и версия алгоритма нарезки, модель,
калибровка токенов. Если ничего не изменилось — «без изменений» за доли секунды.

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `MAX_CHAPTERS` | `40` | сколько глав индексировать (всего 135) |
| `EMBED_MODEL` | `bge-m3` | модель эмбеддингов в Ollama |
| `OLLAMA_URL` | `http://127.0.0.1:11434` | адрес Ollama |
| `PORT` | `5210` | порт веб-интерфейса |
